# Research: IMDb Links on Movie Cards

All open questions from the feature description were already resolved into concrete, testable requirements by the imdb-resolution checklist (`checklists/imdb-resolution.md`) and merged via `spec-amendments.md` before this plan was written — FR-009 and FR-021–FR-023 in particular. The items below are the implementation-shape decisions needed to satisfy those requirements, resolved by grounding in the existing codebase (002-global-search's `useTmdbSearch`/`MovieResultCard` extraction and `scripts/migrate-legacy.ts`'s operational shape are the two closest precedents).

## 1. TMDB call shape for add-time and backfill resolution (FR-007, FR-009)

- **Decision**: Use `GET /movie/{tmdbId}?append_to_response=external_ids` (per the feature description's explicit instruction), not the dedicated `GET /movie/{id}/external_ids` endpoint. Read `external_ids.imdb_id` off the combined response.
- **Rationale**: Explicitly specified in the feature input; also avoids a second round-trip if a future feature needs other `/movie/{id}` fields alongside the IMDb id (not needed today, but the combined-response call costs nothing extra over the dedicated endpoint for a single lookup).
- **Alternatives considered**: The dedicated `/movie/{id}/external_ids` endpoint — functionally equivalent, smaller response, but rejected only because the spec input named the combined-response form explicitly and there's no reason to diverge.

## 2. Split between a throwing low-level fetch and a safe wrapper (FR-008, FR-012)

- **Decision**: `app/lib/tmdb.ts` gets two new exports:
  - `fetchExternalIds(tmdbId: number): Promise<string | null>` — throws on network/HTTP failure, returns `null` when the response has no `external_ids.imdb_id` (a real "no match"). Mirrors `scripts/migrate-legacy.ts`'s existing `resolveTmdbId` shape (throws on API error, returns `null` on no-match) so the same categorization pattern (`api_error` vs `no_tmdb_match`) can be reused by the backfill script.
  - `resolveImdbId(tmdbId: number): Promise<string | null>` — a thin wrapper around `fetchExternalIds` that catches everything (including a bounded timeout via `AbortSignal.timeout(5000)`) and collapses both failure and no-match into `null`. Used by the add-time flow (`addMovieToList`) and the new `external-ids` route handler, both of which must *never* throw past this call (FR-008's "must not block or fail the add", and the route's graceful-absence contract for FR-005).
- **Rationale**: FR-012 requires the backfill report to distinguish "lookup failed" from "no IMDb match found" — that distinction only exists if something in the call chain still throws on failure. But FR-008 requires the opposite guarantee at add-time: a failure must never propagate. One function cannot honor both contracts at once without a boolean "throw-mode" flag threaded through it, which is more indirection than two small functions with one clear job each. This mirrors the existing precedent exactly: `scripts/migrate-legacy.ts`'s `resolveTmdbId` already throws on error today, and nothing in the current codebase has needed a "safe" version of it because only the migration script (which wants the distinction) has called it so far. This feature is the first caller that needs the opposite guarantee.
- **Alternatives considered**: A single `resolveImdbId(tmdbId, { throwOnError: boolean })` — rejected as needless parameterization of a two-line difference; the two-function split reads as two named behaviors rather than one function with a hidden mode switch.

## 3. New Route Handler for search-result lookups (FR-004, FR-005)

- **Decision**: `GET /api/tmdb/external-ids?tmdbId=<id>`, auth-gated the same way as `GET /api/tmdb/search` (`verifySession()`, `401` on failure), calling `resolveImdbId` and always responding `200 { imdbId: string | null }` for any authenticated request — TMDB failures, timeouts, and genuine no-matches are all normalized to `imdbId: null` inside the route itself, never surfaced as a distinguishable HTTP error. The route file also explicitly sets `export const dynamic = "force-dynamic"` (see verification below).
- **Rationale**: A Route Handler (not a Server Action) is required for the same reason `tmdb/search` is one: the client needs `fetch` + `AbortController` to cancel an in-flight lookup when a newer query supersedes it (FR-015) — Server Actions don't expose a client-cancelable transport. Normalizing all failure modes to `{ imdbId: null }` inside the route (rather than mirroring `tmdb/search`'s `503`) is deliberate: FR-005's graceful-absence contract says a search result with an unresolved id must render with "no error... in its place," and per-result lookup failures are expected to be routine at this app's TMDB-call volume (up to 10x normal per query) — a `503` would force every call site to special-case this one endpoint's errors instead of just reading `imdbId` and rendering-or-not, which is the one behavior FR-005 actually asks for.
- **Alternatives considered**: Reusing `tmdb/search`'s `503`-on-failure convention for consistency — rejected because it would push error-shape handling back into `useImdbIds` (research.md §4) for no behavioral benefit; the desired UI outcome (no link, no error) is identical whether the cause was a timeout, a TMDB 500, or a genuine no-match, so collapsing them at the route boundary is simpler than threading three failure reasons through the client just to collapse them there instead.
- **Dynamic-rendering verification (not assumed — checked against the installed Next.js 16.2.11 source, same discipline as this project's Auth.js investigations)**: The concern is the same class of bug that broke production login during 001-movie-watchlist's Phase 7 — a route silently assumed dynamic that wasn't. Verified instead of assumed:
  - `node_modules/next/dist/export/routes/app-route.js:74-85` — when Next attempts to statically export/prerender an app Route Handler, it calls `isStaticGenEnabled(userland)`; if that's `false` **and** `cacheComponents !== true`, it returns `{ cacheControl: { revalidate: 0, expire: undefined } }` and returns *before ever invoking the handler*. The handler body (and therefore `verifySession()`/`cookies()`) is never reached during a static-gen attempt — this is a build-level bail, not a runtime dynamic-API trip.
  - `node_modules/next/dist/server/route-modules/app-route/helpers/is-static-gen-enabled.js:12` — `isStaticGenEnabled` returns `true` only if the module exports `dynamic: 'force-static'`, `dynamic: 'error'`, a `revalidate` of `false` or a positive number, or `generateStaticParams`. None of these apply to a plain `route.ts` that sets none of them.
  - `next.config.ts` (repo root) has no `cacheComponents` key (confirmed via `grep -rn "cacheComponents" next.config.ts` — no match), so `cacheComponents !== true` holds for this project, matching the stated default in `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` ("Route Handlers are not cached by default... opt into caching for `GET`... via `export const dynamic = 'force-static'`").
  - **Conclusion**: this route is guaranteed dynamic (never attempted for static generation, therefore never cached) by the simple absence of those opt-in fields — independent of, and stronger than, "it's dynamic because it reads cookies." The `verifySession()` call provides a *second*, independent layer of protection should `cacheComponents` ever be enabled project-wide in the future: `module.js`'s `case undefined: case 'auto':` branch (`node_modules/next/dist/server/route-modules/app-route/module.js:594`) proxies the request to track Dynamic API usage and bail out of static generation if one is hit, so cookie access would still force a dynamic outcome even under that future config.
  - **Decision, not left to the implicit default**: `app/api/tmdb/external-ids/route.ts` sets `export const dynamic = "force-dynamic"` explicitly anyway, per the instruction to prefer an explicit export over relying on an implicit side effect when there's any doubt. This costs nothing and survives a future `cacheComponents` flip or an accidental `revalidate`/`generateStaticParams` added nearby. Note `app/api/tmdb/search/route.ts` (001-movie-watchlist) has neither this export nor any doubt raised about it at the time — it relies on the same verified-safe implicit default and is out of scope to change here, but is the same latent-risk shape and worth flagging for a future hardening pass.

## 4. Session cache + cancel-on-supersede hook (FR-014, FR-015, FR-016, FR-017, FR-021, FR-022)

- **Decision**: A new hook, `useImdbIds(results: TmdbSearchResult[]): Record<number, string | null>` in `app/components/useImdbIds.ts`, used by both `GlobalMovieSearch.tsx` and `MovieSearch.tsx` (mirroring how both already share `useTmdbSearch`). Internally:
  - Holds a `Record<number, string | null>` in component state, keyed by `tmdbId`, that only grows — never reset between queries within the same mount. This *is* the "session" cache: it lives exactly as long as the search component itself, satisfying FR-014 (reuse across requeries in the same visit) without needing any storage beyond React state.
  - A `useEffect` keyed on `results` (the settled-search array from `useTmdbSearch`) filters out any `tmdbId` already present in the cache (resolved *or* previously failed — both are cached, since a failed lookup within the session is not retried per the Assumptions section's "no automatic retry" stance applied at session scope) and fires one `fetch('/api/tmdb/external-ids?tmdbId=...')` per remaining result, each with its own `AbortController`.
  - The effect's cleanup function aborts every controller it created. Because the effect is keyed on `results` (a new array reference each time a query settles), React runs that cleanup automatically before resolving lookups for the next settled query — this is what satisfies FR-015 (stale lookups from a superseded query never affect current results) with no manual "cancel the previous batch" bookkeeping.
  - Triggering only happens on `results` changing — i.e., only once `useTmdbSearch` has already applied its own 400ms debounce and the fetch has resolved — so no second, independent debounce is introduced (FR-016: "the same debounce delay already applied," achieved by depending on its output rather than duplicating its timer).
  - Volume per settled query is bounded by `results.length` minus whatever's already cached (FR-021) — never independently hardcoded, since `results` itself is already capped at 10 server-side by `app/api/tmdb/search/route.ts:24`.
- **Rationale**: This is the same "extract a small stateful hook shared by both search surfaces" move 002-global-search already made for `useTmdbSearch`/`MovieResultCard` — reusing that precedent instead of inventing a second sharing mechanism (e.g., a global cache object, a context provider) keeps the two features' code shape consistent, and both search surfaces need identical debounce/cache/cancel behavior, so a hook (not a copy-pasted `useEffect` in each component) is justified for the same reason `useTmdbSearch` was: FR-003 (later renumbered FR-004 in this feature) requires matching behavior across both surfaces, and duplicated `useEffect`s are exactly what previously caused the drift risk that extraction fixed.
- **Alternatives considered**: A `Map` in module scope shared across all component instances — rejected: would leak resolved ids across unrelated component mounts (e.g., between the in-list search and global search, or across different lists), which is a bigger scope than "the current session" as FR-014's own example ("the user backspaces and retypes... within the same visit") describes — that visit is scoped to one search box, not the whole app. A `sessionStorage`/`localStorage`-backed cache — rejected as unnecessary persistence beyond a single mount; nothing in the spec requires the cache to survive a page reload, and Assumptions explicitly scopes it to "the search session in which it was resolved."

## 5. Add-time tri-state reuse (FR-023)

- **Decision**: `MovieSnapshot` (`app/(lists)/[listId]/actions.ts`) gains an optional field: `imdbId?: string | null`. Three states map directly to the three cases FR-023 and the Key Entities amendment describe:
  - **`undefined`** (field omitted): no session-cached attempt exists for this movie — `addMovieToList` inserts the row immediately with `imdb_id = NULL` and schedules a background task (via `after()`, see research.md §9) that resolves and persists the id afterward. It does **not** await `resolveImdbId` inline (superseded framing — see §9).
  - **`null`**: the session cache already attempted resolution and found nothing (failure or genuine no-match, collapsed per research.md §2) — `addMovieToList` stores `null` directly, no new lookup, no background task.
  - **`string`**: the session cache already resolved an id — `addMovieToList` stores it directly, no new lookup, no background task.
  - Callers populate this field by reading straight out of the `useImdbIds` cache (`imdbId: cache[result.tmdbId]`, which is `undefined` if the key was never set — JS object-index semantics do this for free, no extra bookkeeping needed) at the moment "add" is invoked (in `MovieSearch.tsx`'s `handleAdd`, and where `GlobalMovieSearch.tsx` constructs the `movie` object passed into `AddToListModal`).
- **Rationale**: FR-023 is explicit that the fallback lookup applies "only when no session-cached identifier exists" — that's a three-way distinction (no attempt / attempted-and-failed / attempted-and-succeeded), not a two-way one, so a plain `string | null` field would conflate "not yet looked up" with "looked up, nothing found" and cause a redundant lookup to be skipped incorrectly (if `null` meant "not yet tried," a real no-match would wrongly trigger a second fetch) or a needed lookup to be wrongly skipped (if `null` meant "not tried," but the field defaulted to `null`, every add would look like a done deal). `undefined`-vs-explicit-`null` is exactly the distinction TypeScript's optional-field semantics already express, so no separate boolean flag is needed alongside it.
- **Alternatives considered**: A separate `imdbIdAttempted: boolean` flag alongside `imdbId: string | null` — rejected as redundant; `undefined` already carries that information for free once the field is declared optional.
- **Wire-serialization verification (not assumed — checked against the installed Next.js 16.2.11 / React Flight source)**: `addMovieToList` is a `"use server"` Server Action called from a Client Component, so `movie` crosses the RSC/Flight wire via `encodeReply`/`processReply`, not a plain in-process function call — this needed checking, not assuming, since a naive `JSON.stringify` would silently drop an `undefined`-valued key.
  - Client encode side: `node_modules/next/dist/compiled/react-server-dom-turbopack/cjs/react-server-dom-turbopack-client.browser.development.js:682` — `resolveToJSON` (the `JSON.stringify` replacer `processReply` uses to serialize the action's argument) has `if ("undefined" === typeof value) return "$undefined";` — an explicit sentinel string, emitted for the property rather than the property being silently omitted.
  - Server decode side: `node_modules/next/dist/compiled/react-server-dom-turbopack/cjs/react-server-dom-turbopack-server.node.development.js:5356-5357` — `parseModelString`'s switch has `case "u": return;` (a bare `return`, i.e. `undefined`), reached when a string value starts with `"$u"` — this is what turns a received `"$undefined"` back into an actual `undefined` when reconstructing the argument object server-side.
  - Confirmed the same in the webpack-bundler variant too (`react-server-dom-webpack-client.browser.development.js:689` and `...server.node.development.js:5359`), so this isn't dependent on which bundler this project's build ends up using.
  - **Finding**: a literal `undefined` property *value* on the `movie` object (e.g. `{ ...snapshot, imdbId: undefined }`) round-trips as `undefined` on the server — it is explicitly preserved via the `"$undefined"` sentinel, **not** collapsed or dropped the way plain `JSON.stringify` would. This is stronger than what was asked to be verified.
  - **Safety net regardless of that finding**: even setting the above aside, the `undefined` branch of this tri-state design is safe by construction. Whether a caller omits the `imdbId` key entirely from the object literal, or includes it with an explicit `undefined` value, both read as `movie.imdbId === undefined` via ordinary JS property access on whichever end evaluates it — an omitted key and an explicit-`undefined` key are indistinguishable to `addMovieToList`'s `movie.imdbId === undefined` check either way. So even if some future Next.js/React version changed the wire behavior to drop the key instead of sentinel-encoding it, the fallback-lookup branch (FR-007/FR-008) would still trigger correctly — the only branch that specifically depends on the verified sentinel behavior is distinguishing an *explicit* `null` from `undefined`, and that distinction was verified above, not assumed.

## 6. IMDb URL construction (Assumptions)

- **Decision**: `https://www.imdb.com/title/${imdbId}/` — IMDb's standard public title-page URL, built in the new `ImdbLink` component, nowhere else.
- **Rationale**: Directly matches the Assumptions section ("IMDb's standard public title-page URL convention; no additional data beyond the identifier itself is needed"). Centralizing the URL template in one presentational component (rather than inlining it at both call sites — list-detail page and `MovieResultCard`) means a future convention change (e.g., a locale-specific IMDb path) is a one-line change.
- **Alternatives considered**: None — this is IMDb's only public URL convention for a title page; no ambiguity to resolve.

## 7. Rendering contract for graceful absence (FR-003, FR-005)

- **Decision**: `ImdbLink` takes `imdbId: string | null | undefined` and renders `null` (nothing — no wrapper element, no placeholder) whenever `imdbId` is falsy. Both call sites (list-detail entry row, `MovieResultCard`) pass whatever they have straight through without pre-filtering.
- **Rationale**: FR-003 and FR-005 both require "no link, no placeholder, no error state" — the simplest way to guarantee that at every call site is for the shared component itself to own the falsy-check, so no call site can independently forget it or render an empty wrapper element that visually reserves space.
- **Alternatives considered**: Each call site pre-checking `entry.imdbId && <ImdbLink .../>` — rejected as duplicated logic across two call sites for something the shared component can guarantee once.

## 8. Backfill script shape (FR-009 through FR-012)

- **Decision**: `scripts/backfill-imdb-ids.ts`, structurally parallel to `scripts/migrate-legacy.ts`: same `--database-url` / `MIGRATION_DATABASE_URL` guard (deliberately ignoring `DATABASE_URL`, same safety rationale as the existing script — this backfill can target a real production database, and an accidental default-DB write is exactly what that guard already prevents), same `TMDB_REQUEST_DELAY_MS = 250` sequential pacing via `sleep`, same `CircuitBreakerAbort` after `CONSECUTIVE_API_ERROR_LIMIT = 5` consecutive `fetchExternalIds` throws, same end-of-run JSON orphan report (written to `scripts/data/backfill-imdb-orphans.json`) distinguishing `api_error` from `no_tmdb_match` categories (FR-012). The query scope is `select * from movie_entries where imdb_id is null` (FR-010's idempotency — already-resolved rows are never selected, so a second run is a fast no-op that reports nothing to do).
- **Rationale**: FR-011 explicitly requires "consistent with this project's existing legacy-data migration approach" — there is exactly one existing precedent to be consistent with, and it already solves sequencing, rate-limiting, circuit-breaking, and reporting in a way this feature's requirements match almost verbatim (FR-010's idempotency ⇔ that script's `onConflictDoNothing` idempotency; FR-012's dual-category report ⇔ that script's `missing_imdb`/`no_tmdb_match`/`api_error` categories). Reusing the shape (not the code — this script only updates one column, it doesn't insert lists/entries) avoids inventing a second operational convention for what is, for this project's admin, the same kind of one-off task.
- **Alternatives considered**: A Drizzle migration-time data backfill (running inside `drizzle-kit migrate`) — rejected: migrations run automatically on deploy in most setups, but this backfill makes N external network calls with deliberate rate-limiting delays, which is categorically different from a schema migration and must stay a manually-invoked, resumable operational script (matching `migrate-legacy.ts`'s own framing, "a manually-run, standalone process," per the Assumptions section).

## 9. Add-time fallback lookup: fire-and-forget via `after()`, not an inline await (FR-007, FR-008)

- **Superseded framing**: research.md §5 and the original plan.md/data-model.md/contracts language described the `undefined`-case fallback as `await resolveImdbId(movie.tmdbId)` performed inline, before the insert, with `resolveImdbId`'s internal `AbortSignal.timeout(5000)` bound cited as what keeps FR-008 satisfied ("a slow/failing call can never *visibly* delay the add" — up to 5 seconds, bounded but not zero). That framing is retired by this section: an *awaited* call, however short its timeout, is still latency the add-time request pays before responding. FR-008 deserves a stronger guarantee than a bound — the add's timing should not depend on TMDB at all.
- **Decision**: `addMovieToList` inserts the `movie_entries` row immediately in the `undefined` case too, with `imdb_id = NULL`, exactly like the `null` case. It then schedules — but does not await — a background task via `after()` (imported from `next/server`) that calls `resolveImdbId(movie.tmdbId)` and, if it returns a non-null id, runs `UPDATE movie_entries SET imdb_id = :id WHERE id = :entryId`. The update is a no-op if the row no longer exists (entry removed in the meantime) — the same no-op-safe idiom already used by `removeMovieFromList` (a `DELETE ... RETURNING` that's simply skipped downstream when it returns nothing) and by the backfill script's idempotent `WHERE imdb_id IS NULL` scoping. Because the update targets the row by its now-known `entryId` (available immediately after the insert), no query-then-update race with a concurrent remove needs separate handling: either the row is present and gets updated, or it's gone and the `UPDATE` affects zero rows.
- **Verification (not assumed — checked against the installed Next.js 16.2.11 source, same discipline as this feature's route-caching and Server-Action-serialization checks)**:
  - `node_modules/next/dist/server/after/after.js` — `after(task)` reads `workAsyncStorage.getStore()` and calls `afterContext.after(task)`; it throws only if called outside a request scope (`workStore` missing), which a `"use server"` Server Action invoked from a request is not. `next/server.d.ts:21` re-exports it: `export { after } from 'next/dist/server/after'`, and `next/server.js:14,29` wires the same export at runtime — so `import { after } from "next/server"` is the correct, currently-recommended import for this codebase.
  - `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md:8` — `after` is explicitly documented as usable in "Server Components..., Server Functions, Route Handlers, and Proxy." A Server Action (`"use server"`) is a Server Function, so `addMovieToList` is a supported call site.
  - Same doc, **Version History** table (line ~302): `after` became stable in `v15.1.0`; `unstable_after` (the experimental predecessor cited in this task's brief) was only the `v15.0.0-rc` name. This project runs Next.js `16.2.11` (`node_modules/next/package.json`), well past stabilization — no `unstable_` prefix, no experimental flag needed.
  - Platform Support table in the same doc: "Node.js server — Yes." This project's deployment target (Vercel, Node.js runtime, confirmed by the absence of any `export const runtime = "edge"` in this route/action tree) is supported.
  - `after`'s own "Duration" section and the doc's collapsed "Reference: supporting `after` for serverless platforms" detail confirm the mechanism: Next.js resolves `after` through a `waitUntil(promise)` primitive read off `globalThis[Symbol.for('@next/request-context')]` — on Vercel, `@vercel/functions`' `waitUntil` (or Vercel's own platform-injected equivalent) is exactly this primitive, extending the serverless invocation's lifetime until the promise settles. `after()` is the framework-level API built on top of it; this project calls `after()` directly rather than reaching for `@vercel/functions`' `waitUntil` itself, since `next/server`'s `after` is the higher-level, platform-portable wrapper and nothing here needs `waitUntil`'s lower-level surface (e.g. running outside any Next.js request lifecycle).
  - **Conclusion**: `after()` from `next/server` is the correct, stable, currently-recommended mechanism for this project's deployment target to schedule the background `resolveImdbId` + `UPDATE` after `addMovieToList` responds.
- **Rationale**: This is a strictly stronger fulfillment of FR-008 than the bounded-timeout framing it replaces — the add's response no longer depends on `resolveImdbId` settling at all, successfully or not, so there is no latency figure to bound in the first place. It also simplifies the `undefined` case to structurally match the `null` case (insert immediately, in both cases with `imdb_id` known-or-pending), leaving `resolveImdbId`'s existing `AbortSignal.timeout(5000)` (research.md §2) as a hygiene bound on the background task's own runtime (so it can't hang indefinitely and starve `after()`'s execution window) rather than as the thing standing between the user and a slow response.
- **Alternatives considered**: Keeping the inline `await` with a shorter timeout — rejected, still couples add latency to TMDB by construction, just with a smaller worst case; doesn't meet the brief's "provably independent of TMDB entirely" bar. A separate queue/job table for the background update — rejected as unjustified infrastructure for a single best-effort `UPDATE`; `after()` is already the framework-native primitive for exactly this shape of work and needs no additional moving parts.

## Summary of new vs. reused vs. modified surfaces

- **New**: `app/components/ImdbLink.tsx`, `app/components/useImdbIds.ts`, `app/api/tmdb/external-ids/route.ts`, `scripts/backfill-imdb-ids.ts`, one Drizzle migration (`movie_entries.imdb_id`).
- **Reused unchanged**: `app/search/AddToListModal.tsx` (already forwards whatever `movie` shape it's given straight through), `app/api/tmdb/search/route.ts`, `useTmdbSearch`, `scripts/migrate-legacy.ts`'s operational pattern (copied in shape, not in code, into the new backfill script).
- **Modified (small, backward-compatible)**: `app/lib/db/schema.ts` (new nullable column), `app/lib/tmdb.ts` (`fetchExternalIds`, `resolveImdbId`), `app/(lists)/[listId]/actions.ts` (`MovieSnapshot.imdbId?`, insert persists it or defers it via `after()` per §9), `app/(lists)/[listId]/page.tsx` and `app/(lists)/[listId]/MovieSearch.tsx` and `app/search/GlobalMovieSearch.tsx` and `app/components/MovieResultCard.tsx` (render/pass through the new id).
