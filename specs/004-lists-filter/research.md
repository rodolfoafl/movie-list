# Research: Filter Lists by Name on the Overview Page

All items below were either dictated explicitly by the feature owner (recorded as such) or resolved by reading this project's actual installed source (`node_modules/`), per `AGENTS.md`'s standing instruction to verify against local sources rather than trained knowledge for this non-standard Next.js version.

## 1. Literal-substring matching mechanism (FR-013, SC-005)

**Decision**: Postgres's `position(needle in haystack) > 0`, both sides lower-cased: `position(lower($filter) in lower(lists.name)) > 0`.

**Rationale**: Directed explicitly by the feature owner. `position()` is a pure substring test — it has no wildcard/escape-character vocabulary at all, so every character of the filter text (including `%`, `_`, and `\`) is compared literally by construction. This satisfies FR-013 structurally rather than procedurally: there is no escaping step that could be forgotten or done wrong, because there is nothing to escape. `lower()` on both sides gives case-insensitivity (SC-002) without touching accents — Postgres's built-in `lower()` case-folds only; it does not accent-fold (that's the separate `unaccent` extension, deliberately not used per spec.md Assumptions). This means the accent-sensitivity requirement (FR-003 — "e" must not match "é") is satisfied automatically as a side effect of not introducing `unaccent`, with no extra logic needed.

**Alternatives considered**:
- `ILIKE '%' || filter || '%'` with manual escaping of `%`, `_`, and the escape character itself (`\`) via `replace()` chains or Postgres's `ESCAPE` clause — rejected per explicit instruction: this is exactly the class of mechanism (manual pattern-escaping) FR-013 is written to make robust against, and a missed or wrong escape order is a realistic, easy-to-introduce bug (e.g. escaping `\` after `%`/`_` instead of before would double-escape).
- `strpos(lower(haystack), lower(needle)) > 0` — functionally identical to `position(... in ...)` (both are plain substring tests, no metacharacters); `position()` chosen only because it reads closer to natural language in the query and both are equally safe. Either is correct; `position()` is used consistently below.

**Verification**: The existing codebase already establishes the pattern of interpolating a plain JS string value into a Drizzle `sql` template alongside a column reference — `app/(lists)/actions.ts:42`, `:93` (`sql\`lower(trim(${lists.name})) = lower(trim(${name}))\``) and `scripts/migrate-legacy.ts:165`. Drizzle's `sql` tag parameterizes non-SQL interpolations automatically (the existing duplicate-name-rejection tests in `tests/integration/lists.test.ts` exercise this exact code path with real apostrophes/whitespace and pass), so `position(lower(${filterValue}) in lower(${lists.name})) > 0` is safe by the same, already-proven mechanism — no new interpolation pattern is introduced.

## 2. Live-filter debounce and URL update mechanism (FR-004, FR-005, FR-014)

**Decision**: A client component (`ListsFilterInput`) holds the input's live value in local state (updates on every keystroke, so the input itself never feels laggy), and a `useEffect` keyed on that value debounces a `router.replace()` call to the settled value after 400ms, mirroring `app/components/useTmdbSearch.ts`'s existing `setTimeout`/`clearTimeout`-in-`useEffect` debounce shape (`DEBOUNCE_MS = 400`).

**Rationale**: Directed explicitly by the feature owner — reuse the app's one existing debounce precedent rather than inventing a second shape or pulling in a debounce library. `router.replace()` (never `router.push()`) is used for every keystroke-driven URL update, which mechanically satisfies FR-005/FR-014's "replace, never push, so Back skips over intermediate filter values" requirement — there is nothing to opt into per-call, since `replace` is the only navigation method this component ever calls.

**Debounce delay**: 400ms, matching `useTmdbSearch`'s `DEBOUNCE_MS` exactly, for consistency of feel across the app's two debounced-input surfaces (spec.md's Assumptions section leaves the exact value to plan time).

**Verified against Next.js 16.2.11's actual docs** (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md`): `router.replace(href)` performs a client-side navigation "without adding a new entry into the browser's history stack" — exactly the FR-005 guarantee, confirmed from source rather than assumed.

## 3. Reading the initial filter value without `useSearchParams()` (avoids a Suspense requirement)

**Decision**: `ListsFilterInput` receives the current filter value as a plain `initialQuery: string` prop from the Server Component page, not via the `useSearchParams()` client hook.

**Rationale**: Per `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-search-params.md`: "If you're already in a Server Component Page, consider using the `searchParams` prop and passing the values to Client Components" — this is the documented-preferred path, and it sidesteps the hook's own documented cost: "a static page that calls `useSearchParams` from a Client Component must be wrapped in a `Suspense` boundary, otherwise the build fails" during production builds. `ListsOverviewPage` already reads the page's `searchParams` prop itself (needed server-side for the query, see §1), which the same doc confirms makes the route request-time/dynamic on its own ("`searchParams` is a Request-time API... opts the page into dynamic rendering"). Passing that already-read value straight down as a prop means the client component never calls `useSearchParams()` at all, so no `<Suspense>` boundary is required anywhere for this feature. `router.replace()` itself needs no `usePathname()` companion since this page has exactly one route (`/`) and exactly one query param (`q`) to manage — the target href is built directly as `` `/?q=${value}` `` (or `/` when empty), with no other params to preserve.

**Alternatives considered**: `useSearchParams()` + `usePathname()` (the pattern shown in the docs' own "Updating searchParams" example) — works, but adds a hook, a Suspense boundary requirement, and pathname-merging logic this single-route feature doesn't need. Rejected as unnecessary indirection.

## 4. Server-side query location and shape (FR-006; "Recurring drift class" precedent)

**Decision**: The candidate set is narrowed entirely in the SQL `WHERE` clause, in a new small `app/(lists)/queries.ts` module (`getVisibleLists(filterValue)`, `hasAnyLists()`), called from the page. No client-side `.filter()`/`.includes()` over an unfiltered fetch anywhere.

**Rationale**: Directed explicitly by the feature owner, and directly reinforced by `specs/notes.md`'s 2026-07-25 "Recurring drift class (T035)" entry — the same deviation (data-model/spec says query-time WHERE, implementation does an in-memory JS filter) has already happened once in this project and was flagged as a *pattern*, not a one-off. `app/(lists)/[listId]/page.tsx`'s existing `watchedCondition`/`and(...)` branching is the direct precedent this feature extends, applied to the sibling overview page.

**Why a new `queries.ts` instead of inlining in `page.tsx` (as `[listId]/page.tsx` does today)**: FR-013/SC-005 is a specific, easy-to-silently-break correctness property (a future edit could reintroduce `ILIKE` or break the escaping-free guarantee without any type error). Extracting the two query functions gives them a stable export that an integration test can call directly against `TEST_DATABASE_URL` — proving the literal-substring property against a real Postgres instance (Neon's `position()` behavior, not assumed) rather than relying on manual/browser verification alone for a property this load-bearing. This mirrors 003-imdb-links' research.md §2 rationale for splitting `resolveImdbId` out of inline call sites: extraction here is justified by a concrete verification need, not speculative reuse.

## 5. Distinguishing "no lists at all" from "no lists match the filter" (FR-007)

**Decision**: `hasAnyLists()` — a cheap `SELECT lists.id FROM lists LIMIT 1` existence check — is only ever called when the filtered query already returned zero rows AND a filter is active. When the filtered query returns any rows, or no filter is active, the filtered result set alone is sufficient to decide which of the two messages (or neither) to show, with zero extra queries.

**Rationale**: FR-007 requires the "no lists match" message to appear only when lists exist overall; if the workspace has zero lists in total, the pre-existing "Nenhuma lista criada ainda." message must still win even with a filter value in the URL (e.g. a stale bookmarked `?q=` link visited before any list was ever created) — otherwise a user with truly zero lists would see a message implying lists exist somewhere but don't match, which is false. The extra existence check only runs on the one path where it's needed (filtered-and-empty), keeping the common cases (results found, or no filter applied) at exactly one query, matching the page's current query count today.

## 6. Two-column responsive layout mechanism and its tab-order trade-off (FR-001, FR-002, FR-009, FR-010)

**Decision**: A CSS Grid wrapper (`grid gap-4 sm:grid-cols-2`, same `sm:` breakpoint token — 640px — already used throughout this codebase, e.g. `CreateListForm`'s `sm:flex-row`), with the create-list form rendered **first** in DOM/source order and the filter input second. The filter input carries `order-first sm:order-none` — `order-first` (Tailwind's `order: -9999`) moves it visually ahead of the form below `sm:`, and `sm:order-none` cancels that override at `sm:` and above, letting DOM order (form, then filter) govern visual order there — so the create-list form appears left and the filter right on wide viewports, while the filter appears above the form when both stack below `sm:`.

**Rationale**: FR-001 and FR-002 are, read together, an explicit breakpoint-dependent *visual*-order requirement (filter-first on mobile, form-left/filter-right on desktop) that cannot be satisfied by a single fixed DOM order alone — some form of visual reordering across the breakpoint is unavoidable, so the real decision is *which* breakpoint absorbs the resulting Tab-order/visual-order mismatch. Putting the create-list form first in DOM order means desktop's Tab order matches its visual order exactly (form, then filter — `sm:order-none` removes any override there), which is deliberately the breakpoint where the mismatch is avoided: desktop/laptop use is where keyboard-only and screen-reader users are proportionally more common, so that's where visual and Tab order should agree. The *reachability* half of FR-009 ("focusable in a logical tab order") still holds unconditionally at every breakpoint regardless of this choice — the filter input is always reachable by Tab, never skipped, on both mobile and desktop.

**Trade-off accepted, documented rather than hidden**: below `sm:` (mobile), Tab order stays form → filter even though `order-first` makes the filter appear visually above the form — a same-column, two-sibling-control mismatch between visual and DOM order. This is deliberately where the trade-off lands: mobile is overwhelmingly touch-first (tap targets, not Tab traversal), so a Tab-order/visual-order mismatch is lower-impact there than the equivalent mismatch would be on desktop, where keyboard/screen-reader navigation is proportionally more common. FR-009's keyboard requirement is scoped to the filter input's own operability (focusable, typeable, clearable), not a cross-component "Tab must trace the visual grid" requirement, and the two controls are functionally independent (per spec.md's Edge Cases: "the create-list form and the filter operate independently"), so this is a low-severity, common pattern (the same one Tailwind's own `order-*` utilities, and most responsive framework grids, exist for) rather than a functional defect. Recorded here so a future reviewer doesn't need to re-derive why the DOM order and breakpoint split were chosen this way.

**Alternatives considered**: Duplicating the two controls in the DOM (one hidden set per breakpoint) — rejected as needless complexity and an accessibility regression of its own (duplicate landmarks/labels, screen readers announcing both). Rendering order via JS (`useMediaQuery` + conditional JSX) — rejected: turns two static, always-visible form controls into something that depends on client JS and a resize listener for a purely presentational reorder, and reintroduces a hydration-mismatch risk (server doesn't know viewport width) that pure CSS `order` doesn't have.

## 7. `.where(undefined)` is a safe no-op filter (used for the "no filter active" branch)

**Verified directly against the installed driver's source** (`node_modules/drizzle-orm/pg-core/query-builders/select.js:580-590`): `.where(where)` unconditionally does `this.config.where = where; return this;` with no special-casing — passing `undefined` simply leaves `config.where` unset, identical to never calling `.where()` at all. This confirms `getVisibleLists` can pass a single conditionally-`undefined` `SQL` expression straight into one `.where()` call rather than branching into two separate query-builder chains (the shape `[listId]/page.tsx` uses today for its two-armed `watchedCondition ? and(...) : eq(...)` — not needed here since the overview query has only one possible condition, not two to combine).

## 8. No index added for the `position()` filter

**Decision**: No new index is added to support `getVisibleLists`'s filtered query — it stays a plain sequential scan with the `position(lower($q) in lower(name)) > 0` predicate evaluated per row.

**Rationale**: `position()` is a substring test, which by its nature can't be served by a standard B-tree index the way an equality or prefix (`LIKE 'foo%'`) predicate can — supporting it would require something like `pg_trgm`'s trigram GIN index, an extra Postgres extension with no evidence of availability on this project's Neon-hosted database (the same "don't assume an unverified extension is available" reasoning spec.md's Assumptions already applies to `unaccent`, §1). More importantly, it isn't needed: this is a 2-user shared workspace (`plan.md`'s Scale/Scope) whose `lists` table has never had pagination or an indexing concern in the first place — the overview page already fetches the *entire* table on every unfiltered render today (`app/(lists)/page.tsx`, pre-existing `orderBy(asc(lists.name))` with no `LIMIT`). Adding an index to filter a table small enough to already be fetched in full unfiltered would be optimizing a dimension (query latency at scale) this feature has no requirement against (SC-001 only asks that narrowing "feel immediate" for a user with "10+ lists," not that it scale past what a sequential scan already handles instantly). If list count ever grows enough for this to matter, that's a distinct, future optimization decision — not one this feature's spec or success criteria call for.
