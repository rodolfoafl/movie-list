# Research: Global Movie Search

All items below were previously open design questions; the feature owner's steering message (recorded verbatim in this plan's input) already resolved four of them directly. The rest are resolved here by grounding in the existing codebase (see citations).

## 1. Batch-add orchestration (FR-009, FR-012, FR-021, FR-022, FR-023)

- **Decision**: The modal's confirm handler calls a single Server Action, `confirmAddToLists(listIds, movie)` (in `app/search/actions.ts`, see [[contracts/confirm-add-to-lists]]). Internally, `confirmAddToLists` checks the session once, then fans out to a **one-list-at-a-time Server Action**, `addMovieToListWithOutcome(listId, movie)` (see [[contracts/add-movie-to-list-with-outcome]]), once per checked-and-enabled list, via `Promise.allSettled` — now running server-side inside `confirmAddToLists` rather than client-side in the modal. `addMovieToListWithOutcome`'s body still does nothing but (a) check the list still exists, (b) call the existing `addMovieToList` from `app/(lists)/[listId]/actions.ts:20` **unchanged**, and (c) translate the outcome to a plain `{ status: "success" | "failure"; reason?: string }` value. No new batch-insert SQL, no array-typed mutation action — the per-list DB work is still one row at a time, inside `addMovieToList`, unchanged.
- **Rationale**: This satisfies the steering instruction literally — `addMovieToList` is reused unchanged, called N times, fanned out with `Promise.allSettled`. The one-list wrapper is required (not optional) for a concrete reason found while grounding this in the framework: Next.js sanitizes thrown Server Action errors before they reach the client in production (only a `digest` survives; custom fields like a Postgres error `.code` do not). `addMovieToList` deliberately returns expected errors as *values* but still `throw`s on unexpected DB errors (`app/(lists)/[listId]/actions.ts:53`). If the client called `addMovieToList` directly and a checked list had been deleted mid-flight, the resulting foreign-key violation would arrive client-side as an opaque, non-inspectable rejection — making FR-021's specific "lista não existe mais" reason impossible to produce from the client. Classifying the outcome must happen server-side, where the DB error is still concrete.
- **Classification rules** (implemented inside the wrapper, server-side):
  - List row no longer exists (checked via `select id from lists where id = :listId` before calling `addMovieToList`, mirroring the existing select-then-act idiom already used in `addMovieToList`/`createList`) → `{ status: "failure", reason: "Lista não existe mais." }` (FR-021), without calling `addMovieToList` at all.
  - `addMovieToList` returns `undefined` (inserted) → `{ status: "success" }`.
  - `addMovieToList` returns `{ error: "already_in_list" }` → `{ status: "success" }` (FR-022 — the desired end state already holds, whether that's because of this feature's own concurrent add or the pre-existing in-list search).
  - Any other thrown error → caught inside the wrapper, `{ status: "failure", reason: "Não foi possível adicionar, tente novamente." }` (FR-023's example wording, used verbatim).
- **Alternatives considered**: A single new "batch add" Server Action taking `listIds: string[]` and looping server-side — rejected because it's exactly the "new batch-mutation mechanism" the steering message ruled out, and it gains nothing over N calls to a one-list wrapper (Promise.allSettled already gives per-call isolation). Inspecting thrown-error shape client-side — rejected per the sanitization issue above.
- **Session-check placement**: `addMovieToListWithOutcome`'s own `verifySession()` runs once per call, so if the client fanned out to it N times directly, a session that expires mid-confirmation would trigger up to N near-simultaneous `redirect()` calls — one per `Promise.allSettled` branch — instead of one. **Decision**: consolidate the whole confirm-flow orchestration into `confirmAddToLists`, a single Server Action that calls `verifySession()` exactly once at the top, then internally runs `Promise.allSettled` over `addMovieToListWithOutcome(listId, movie)` for each `listId`. The modal now makes exactly one action call per confirmation (`await confirmAddToLists(checkedEnabledListIds, movie)`) instead of building its own client-side `Promise.allSettled` over N calls, so this is a strictly simpler shape than the earlier two-action design (a separate `verifyAddToListsSession()` plus client-side fan-out) — one new action instead of two, and the orchestration lives in one place instead of being split between client and server. `addMovieToListWithOutcome`'s own `verifySession()` (unmodified) is kept, not removed — it's still an independently exported, directly-callable Server Action, so it cannot rely on an auth check performed by whatever happens to call it. In the normal flow (called by `confirmAddToLists` milliseconds after that action's own check) this second check is cheap and passes silently. See [[contracts/confirm-add-to-lists]].

## 2. Modal list-set snapshot fetch (FR-010, FR-019)

- **Decision**: A new Server Action `getListsForMovie(tmdbId: number)` (in `app/search/actions.ts`) returns `{ id, name, alreadyInList }[]` for every list in the workspace. The modal calls it exactly once, in a `useEffect` keyed on `[isOpen, movie.tmdbId]`, when transitioning from closed to open, and stores the result in local component state — never refetched for the remainder of that open instance, satisfying FR-019.
- **Rationale**: No existing helper computes "which lists contain movie X" across *all* lists — the only precedent (`app/(lists)/[listId]/page.tsx:49-52`) scopes to one list. The new action is two simple `db.select` queries (all lists; all `movieEntries` rows for that `tmdbId`) joined in memory via a `Set`, matching the codebase's existing preference for plain, un-nested Drizzle queries over hand-written joins. A Server Action (not a Route Handler) was chosen for symmetry with `addMovieToList`/`createList`/`addMovieToListWithOutcome`, which are all Server Actions the modal already calls as plain async functions — introducing a Route Handler here would be a second data-fetching convention for one read.
- **Alternatives considered**: A `GET /api/lists/for-movie` Route Handler (matches the `tmdb/search` precedent) — viable but rejected to avoid mixing two fetch idioms inside one new component; documented here in case review prefers consistency with the TMDB route instead.

## 3. Inline create-list-from-modal (FR-013, FR-014, FR-024, FR-025)

- **Decision**: The modal renders the existing `createList` Server Action (`app/(lists)/actions.ts:16`) through `useActionState`, exactly like `CreateListForm.tsx:9` already does — same validation, same inline error strings, unchanged. The one small, backward-compatible change: `createList`'s success return changes from implicit `undefined` to `{ id, name }` (still no `.error` field, so `CreateListForm.tsx`'s existing `if (!result?.error)` check keeps working unmodified), by capturing `.returning({ id: lists.id })` on the insert it already performs (`app/(lists)/actions.ts:46`).
- **Rationale**: FR-014/FR-025 require that after creating a list inline, the user can immediately select and confirm it *without redoing the search* — i.e., without a snapshot re-fetch, which FR-019 forbids anyway. The modal needs the new list's `id` to append it to its in-memory snapshot as an unchecked, enabled entry (a brand-new list cannot already contain the movie). Without returning the id, the modal would have no way to know what was just created except by re-querying, which is exactly what FR-019 rules out.
- **Alternatives considered**: Re-fetching the snapshot after inline creation — rejected, directly contradicts FR-019. Reimplementing list-creation validation inside the modal — rejected, explicitly ruled out by both FR-024 and the steering message ("reuses `createList`'s existing validation").

## 4. Modal implementation (no existing Dialog primitive)

- **Decision**: Use the native HTML `<dialog>` element (`dialogRef.current.showModal()` / `.close()`), not a hand-rolled overlay `<div>`.
- **Rationale**: Grepping the codebase found zero existing modal/Dialog components and no Radix/shadcn/headlessui dependency — confirmations today use plain `window.confirm(...)` (`app/(lists)/ListRow.tsx`). FR-018 requires full keyboard operability and CLAUDE.md requires Lighthouse accessibility ≥ 90; native `<dialog>` provides focus trapping, Escape-to-close, and top-layer stacking for free, which a hand-rolled overlay would have to reimplement and would be easy to get subtly wrong (focus trap edge cases are a common a11y regression source). The dialog's native `close` event (fired on Escape or a form's `method="dialog"` cancel) is used to sync back to React state and satisfies FR-015 (closing without confirming changes nothing) automatically, since no mutation is wired to that event.
- **Alternatives considered**: A custom `role="dialog"` overlay with a hand-rolled focus trap — rejected as unnecessary risk/effort given `<dialog>` covers the same requirements natively and React 19 supports it without a wrapper library.

## 5. Shared search UI between in-list and global search (FR-003)

- **Decision**: Extract the debounce/fetch state machine and the result-card markup currently inline in `app/(lists)/[listId]/MovieSearch.tsx` into two shared pieces — a hook `useTmdbSearch(query)` and a presentational `MovieResultCard` component (both under `app/components/`) — parameterized by a `renderAction` slot for the per-context "add" affordance. `MovieSearch.tsx` is refactored to consume them (existing list-scoped add-button behavior preserved exactly); the new `GlobalMovieSearch.tsx` consumes them with an action that opens `AddToListModal` instead.
- **Rationale**: FR-003 requires the global result presentation to match the in-list one. Extracting shared code makes that a structural guarantee instead of a manually-maintained convention across two ~150-line components that would otherwise drift. This is the one place this plan deviates from the codebase's general tolerance for small duplication (seen in `createList`/`renameList`'s duplicated validation) — justified because here the duplication is a spec requirement (FR-003), not incidental.
- **Alternatives considered**: Copy-pasting `MovieSearch.tsx` into `GlobalMovieSearch.tsx` wholesale (matching the `createList`/`renameList` precedent) — rejected because FR-003's "matching presentation" requirement is directly undermined by two independently-editable copies; flagging this alternative explicitly since it does match existing codebase style, in case review prefers it.

## 6. Reachable entry point (FR-001)

- **Decision**: Add a small `AppHeader` component (`app/components/AppHeader.tsx`) rendered from `app/layout.tsx`, with two links: "Minhas listas" (`/`) and "Buscar filmes" (`/search`).
- **Rationale**: `app/layout.tsx:31` currently renders only `<main>{children}</main>` — there is no nav of any kind, so FR-001 ("reachable from anywhere") has no existing hook to attach to. spec.md's own Assumption states placement is a planning-phase decision and explicitly does not require "a new navigation/menu system," so the smallest thing that makes the search page reachable from every page (a persistent two-link header in the root layout) is used rather than building out a fuller nav.
- **Alternatives considered**: A link only from the lists-overview page — rejected, doesn't satisfy "from anywhere" for someone on a list-detail page.

## 7. TMDB search reuse (FR-006)

- **Decision**: `GlobalMovieSearch` calls the existing `GET /api/tmdb/search` Route Handler (`app/api/tmdb/search/route.ts`) unchanged, via the shared `useTmdbSearch` hook from §5. No new TMDB client code, no new route.
- **Rationale**: Directly mandated by FR-006 and the steering message; the existing handler already does everything needed (debounce is client-side, trimming/slicing/error-mapping already handled server-side).

## 8. Redirect-error propagation on session expiry mid-fan-out (Phase 4 review finding)

- **Decision**: Use `unstable_rethrow` (from `next/navigation`), not `isRedirectError`, and apply the same check at **both** layers: inside `addMovieToListWithOutcome`'s `catch` block (around its call to `addMovieToList`) **and** inside `confirmAddToLists`'s `Promise.allSettled` result-mapping (see [[contracts/add-movie-to-list-with-outcome]], [[contracts/confirm-add-to-lists]]).
- **Rationale**:
  - `isRedirectError` is not exported from `next/navigation` in this project's Next.js version (16.2.11) — confirmed absent from both `navigation.js`'s export list and `navigation.d.ts` in `node_modules/next/dist/client/components/`; it has become a private implementation detail (still used internally, e.g. by `is-next-router-error.js`). Next's own docs (`unstable_rethrow.md`) now recommend `unstable_rethrow` for exactly this pattern — rethrowing a framework control-flow error (redirect/notFound/forbidden/unauthorized) caught by an application `try/catch`, letting anything else fall through. It performs the same `isRedirectError` check internally, so it is a compatible, currently-public replacement.
  - **Both layers needed the fix, not just one.** `addMovieToListWithOutcome`'s `try/catch` wraps its call to `addMovieToList` (`app/(lists)/[listId]/actions.ts:20`), which itself calls `verifySession()` again at its own top — that nested call, not `addMovieToListWithOutcome`'s own unguarded step-1 `verifySession()`, is where a session-expiry redirect thrown mid-fan-out actually originates and was previously caught and converted to the generic failure reason. But rethrowing there only turns that one call's promise into a rejection; `confirmAddToLists`'s `Promise.allSettled` catches that rejection as a normal settled result (`{ status: "rejected", reason: <redirect error> }`), and its surrounding `.map` previously converted *every* rejected result into the generic failure literal unconditionally, without ever inspecting `result.reason` — silently discarding the redirect error a second time, one level up. Confirmed empirically: running the new integration test (see [[contracts/confirm-add-to-lists]]) against a single-layer fix (only `addMovieToListWithOutcome`) still resolved to an array of outcomes instead of rejecting; only adding `unstable_rethrow(result.reason)` to `confirmAddToLists`'s mapping made the redirect propagate all the way out.
- **Alternatives considered**: Fixing only `addMovieToListWithOutcome`'s catch block, per the literal original bug report — rejected once the integration test demonstrated the second swallow point in `confirmAddToLists` itself.

## Summary of new vs. reused vs. modified surfaces

- **New**: `app/search/page.tsx`, `app/search/GlobalMovieSearch.tsx`, `app/search/AddToListModal.tsx`, `app/search/actions.ts` (`getListsForMovie`, `addMovieToListWithOutcome`, `confirmAddToLists`), `app/components/AppHeader.tsx`, `app/components/MovieResultCard.tsx`, `app/components/useTmdbSearch.ts`.
- **Reused unchanged**: `addMovieToList`, `createList`'s validation logic, `GET /api/tmdb/search`, `isUniqueViolation`, DB schema (no migration needed — no new tables/columns).
- **Modified (small, backward-compatible)**: `app/(lists)/actions.ts` (`createList`'s success return gains `{id, name}`), `app/(lists)/[listId]/MovieSearch.tsx` (refactored onto the shared hook/card, behavior unchanged), `app/layout.tsx` (renders `AppHeader`).
